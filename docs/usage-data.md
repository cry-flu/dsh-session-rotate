# 用量数据与实测参考

这份文件收的是「这个插件到底改变了什么」的全部观察记录 —— 数字、口径、复算方法，以及**不能从这些数字里读出来的结论**。README 里只留一张表和一句话，限制与待补都在这儿。

## 数据从哪来

2026-11-08 从平台导出的 `usage_data_*.zip`（每天一个 zip，内含 `amount-*.csv` 与 `cost-*.csv` 两个文件）按日汇总。原始导出不入库（`usage-raw/` 已在 `.gitignore` 里）。

复算用 `tools/usage-summary.ps1`，直接读 zip 或解压后的目录：

```powershell
pwsh -File tools\usage-summary.ps1 -Path <usage.zip 路径>
# | 2026-11-07 | 1,418 | 85,801,186 | 98.2% | 6.3266 | 60,509 | 0.446 |
```

## 口径

- 请求数 = `request_count` 求和；
- token 总量 = `input_cache_hit_tokens` + `input_cache_miss_tokens` + `output_tokens`；
- 缓存命中率 = hit ÷ (hit + miss)；
- 花费 = `cost` 列的 `cost`（CNY）求和；
- 平均每次请求 token、每 100 次请求花费，由前四列除算得出。

## 时区（每个口径用哪种，写死在这里）

| 数据源 | 时间戳形态 | 用到的地方 | 归日方式 |
| --- | --- | --- | --- |
| 平台 CSV | `start_time_iso` 带 `+08:00` 偏移，例如 `2026-11-03T00:00:00+08:00` → `2026-11-03T01:00:00+08:00` | 下表三个日期、小时段数 | **本地日（UTC+8）**，小时段也是本地小时 |
| 插件 `debug.log` | 行首 UTC，末尾带 `Z`，例如 `2026-11-03T16:03:47.858Z` | 换新次数、加载记录 | **先 +8 小时换算成本地时间再归日** |

所以：下表的「2026-11-03」指本地 11-03 00:00–23:59（UTC `2026-11-02T16:00Z` → `2026-11-03T15:59Z`）；下文「换新次数按日」也一律是本地日，不是日志里那串 UTC 日期。

## 每日汇总

| 日期 | 请求数 | token 总量（输入+输出） | 缓存命中率 | 花费（CNY） | 平均每次请求 token | 每 100 次请求花费（CNY） |
| --- | --- | --- | --- | --- | --- | --- |
| 2026-10-31 | 1,565 | 218,093,582 | 97.3% | 14.6912 | 139,357 | 0.939 |
| 2026-11-03 | 273 | 38,111,601 | 96.4% | 2.9166 | 139,603 | 1.068 |
| 2026-11-07 | 1,418 | 85,801,186 | 98.2% | 6.3266 | 60,509 | 0.446 |

三行都是**可复算**状态：把对应的整日导出 zip 交给 `tools/usage-summary.ps1 -Path <zip>`，就能逐位重出表里这七列。口径固定、没有隐含假设：token 总量 = cache hit + cache miss + output，命中率 = hit / (hit + miss)，`¥` 是 `cost` 列求和。下面每个日期都写明这一行的复算依据（文件名、行数/时段数；11-03 另附一次实际复算输出）：

- `2026-10-31`：`usage_data_2026-10-31_2026-10-31.zip`，68 行 amount / 17 个小时段；
- `2026-11-03`：`usage_data_2026-11-03_2026-11-03.zip`（12 KB），49 行 amount / 13 行 cost / 12 个小时段（`00:00`、`13:00`–`23:00`，凌晨 1 点到中午 12 点没有量），复算输出 `273 / 38,111,601 / 96.4% / 2.9166 / 139,603 / 1.068`；
- 2026-11-07：`usage_data_2026-11-07_2026-11-07.zip`，64 行 amount / 16 个小时段。

只要拿到同名的整日导出，任何人都能重跑这三行；没有留存导出就无法复算，而不是「大概是这个数」。

另有 11-03 23:27 的一次导出，汇总为 192 次请求、约 3310 万 token、¥2.47 —— 与上表那份**不是同一次导出**，请求数与 token 都对不上，说明时段或口径不同（23:27 导出可能没含当天最后半小时到午夜）。表里用上面那份整天导出，两份不要混着读。

## 一句话结论

平均每次请求 token 从 139,357（10-31）掉到 60,509（11-07），约 -57%；但这三天的请求量差着一个数量级（1,565 / 273 / 1,418），而且 11-07 当天插件版本还是 0.2.1–1.0.0 —— 这些数字是**观察到的现象**，不是「插件省了多少」的因果结论。

## 读这张表之前先看五条

1. 单用户、单环境（Windows 桌面版 + `deepseek-flash`）的数据；三天工作量不同（请求数 1,565 / 273 / 1,418），**量不一样的日子不能直接横比**。
2. 同期还做了别的改动：停掉自动回复、归档长会话、加省 token 规则。下降不能全归功于本插件。
3. 11-03（本地日）插件还没加载过：本机 `debug.log` 最早一条 `已加载` 是 `2026-11-03T16:03:47Z`（= 本地 2026-11-04 00:03），首次真实换新在 `2026-11-03T16:07:27Z`（本地 11-04 00:07）；日志没有轮转文件，只有这一份。也就是说本地 11-03 当天一次换新都没有（此前写成「当天下午已有换新」，是把日志里的 UTC 时间当本地时间读错了）。所以 11-03 和新装的 11-04 可以一起当「插件之前」看，但要注意 11-03 只有 `00:00` 与 `13:00`–`23:00` 有量。
4. 11-07 当天插件版本是 0.2.1–1.0.0（`CHANGELOG` 里 1.1.0 记的是 2026-11-08），不是 1.4.1；1.2.0 之后的延迟归档、1.3.x 的跳转开关都没有体现在这两组数据里。
5. 11-03 的 CSV 里另有 4 次 `function_call` 计数，不是 token，未计入上表。
